Sidebar at scale — 4 directions

Same sample week in every mock: 14 shorts, ~4 a day across 5 days. Delete rows, collapse groups, search and filter — everything is interactive, so judge each idea by using it, not just looking at it.

A. Group by day

Your idea: one section per day, newest first. Old days collapse; counts stay visible.

  • Pro: matches how you think ("today's 4 shorts"); old work disappears without deleting.
  • Con: one short can still show as two rows (source + rendered output); a rendering short is buried under its day.
Build: stamp createdAt on each studio draft (backfill from first-seen), add a group-by-day helper, collapsible group headers. Small change.

B. Group by status

Rows grouped by what needs you: failed and rendering on top, posted collapsed at the bottom.

  • Pro: fastest to build; the action items are always visible no matter the volume.
  • Con: no sense of time; "Ready to post" still grows unbounded at 4 shorts a day.
Build: regroup the existing sidebar list by status — no new data stored. Smallest change.
Sources

C. One row per short, grouped by day Recommended

Fixes the actual duplication: source file + rendered output merge into a single row with file chips, then grouped by day like A.

  • Pro: 14 shorts read as 14 rows, not ~20; day groups stay short even as volume grows.
  • Con: needs the input-to-output link to be reliable (it is — render history already stores both paths).
Build: merge rows sharing an input/output link from render history, then group by day as in A. Medium change, kills two problems at once.
Sources

D. Search + filter + bulk cleanup

Flat compact list with search, status chips, checkboxes and "remove selected". Management tool for heavy days.

  • Pro: scales to any volume; clearing a week's posted shorts takes seconds.
  • Con: weakest overview — works best paired with A or C, not alone.
Build: filter + selection state in the sidebar; reuse the remove logic already shipped. Medium change.
